## 1. システム全体像

利用者がアプリ（Flutter Web）から駐車区画を時間指定で事前予約し、入庫時にアプリから DOWN 指示を出すと、クラウド（App Service）が IoT Hub のダイレクトメソッド経由で AUTOSTAND（ロック板）を下げて入庫を許可する。入出庫はデバイスの満空センサーが検知してテレメトリを返し、Azure Functions が在車記録（UsageRecord）と予約状態を更新する。UP（板上げ）は安全のためデバイス側が空車検知＋安全条件で自律実行し、クラウドは記録のみを行う。終了時刻経過かつ空車になった時点で予約を完了確定し、予約枠料金＋超過料金を算定する。全状態遷移は「現在状態を WHERE に含めた条件付き UPDATE」で競合を排除し、料金・在車・冪等性はテーブル制約と UsageRecord を真実の源として担保する。

## 2. ドメインモデルと状態機械

### 主要エンティティ（DDL 準拠）

| テーブル | 役割 | 重要制約 |
| --- | --- | --- |
| `[User]` / `Consent` | 会員・規約同意 | `UQ_User_email`、論理削除（status=withdrawn） |
| `ParkingSpot` | 駐車区画 | `occupancy`(occupied/vacant) は**表示・availability・物理占有事前判定専用** |
| `Device` | AUTOSTAND、区画と 1:1 | `UQ_Device_spot`、`plate_position`(up/down)、`last_seen_at`（健全性） |
| `Reservation` | 予約。状態機械の中心 | `CK_Resv_status`(6状態)、時刻は UTC |
| `UsageRecord` | 予約期間内の入出庫（複数可） | open行(exit_time NULL)の有無が**在車・ノーショー判定の真実源** |
| `Fee` | 予約と 0..1 | `UQ_Fee_resv`（1予約1行）、`total` は PERSISTED 計算列 |
| `CommandLog` | DOWN 指示の監査・冪等 | `UQ_Cmd_request`（request_id 冪等キー）、result(pending/success/failure) |
| `DeviceEvent` | デバイス状態遷移の記録 | event_type(down_exec/up/entry/exit) |
| `Notification` | 通知ログ | status(queued/sent/failed) |
| `RefreshToken` | ※認証設計§7にのみ存在、**正DDL未反映（gap G1）** | token_hash, family_id, revoked_at |

### 予約状態 × デバイス状態 × 遷移トリガ

デバイス状態（ブロック中／予約待機／入庫待ち／在車中／超過中）は**列に持たず**、予約状態＋plate_position＋open UsageRecord＋未完了 DOWN から導出する。

| 予約状態 | デバイス状態 | 遷移のトリガ | 種別 |
| --- | --- | --- | --- |
| reserved（開始前） | ブロック中 | — | — |
| reserved（開始後・未入庫） | 予約待機→(DOWN)→入庫待ち | gateDown → IoT ダイレクトメソッド | HTTP→IoT |
| active（利用中） | 在車中（一時外出は予約待機/入庫待ち） | 初回 onEntryDetected で reserved→active | IoT |
| overstay（超過） | 超過中 | detectOverstay：end 経過＋open UsageRecord 有 で active→overstay | タイマー |
| completed（完了） | ブロック中 | end 経過＋空車：onExitDetected（即時）or autoComplete（安全網）で →completed＋Fee確定 | IoT / タイマー |
| cancelled | ブロック中 | cancelReservation（reserved のみ可） | HTTP |
| no_show | ブロック中 | detectNoShow：開始＋猶予経過＋UsageRecord 無 で reserved→no_show | タイマー |

- **DOWN はアプリ操作のみ**が契機。**UP はデバイス側**が空車検知＋§5.3安全条件で自律実行（onPlateUp で記録のみ）。
- 完了の駆動契機は一元化：「終了時刻経過 かつ 空車（open UsageRecord 無）」が真の瞬間。退出が後＝onExitDetected が即確定、終了時刻が後＝autoComplete が次走査で確定。両者とも `WHERE status IN ('active','overstay')` で二重確定防止。

## 3. 横断する不変条件（実装時に必ず守る）

| 不変条件 | なぜ |
| --- | --- |
| **状態遷移は「現在状態を WHERE に含めた条件付き UPDATE」、更新0件=競合** | タイマー確定とユーザー操作、IoT 再配信の競合・二重処理を防ぐ。refresh ローテーションにも適用 |
| **時刻はすべて UTC 保存（DATETIME2+SYSUTCDATETIME）、表示時に JST** | 期間比較・タイマー走査の基準を一意にする |
| **SQL は必ずパラメータ化。重複/近接予約は serializable Tx 内で競合チェック→INSERT** | SQLi 防止。Azure SQL に範囲排他制約が無いため、バッファ込み重なり判定をアプリで担保 |
| **DOWN は冪等。CommandLog.request_id(UNIQUE) で重複吸収。1操作=新request_id、試行ごと1行、pending→結果update** | トランスポート再送（at-least-once）でロック板が二重作動しないように |
| **ノーショー・在車判定は occupancy ではなく UsageRecord(open行)の有無** | occupancy は物理センサーの揺らぎを含む。課金・遷移の判断はアプリ記録を真実源に |
| **完了確定は条件付き UPDATE が1件成功したときだけ Fee を INSERT** | `UQ_Fee_resv` 違反回避。onExitDetected/autoComplete の二重確定で Fee 重複を防ぐ（最初に踏む石） |
| **onEntryDetected の UsageRecord 挿入は「open行があれば挿入しない」で冪等化** | IoT 再配信で在車記録が二重行にならないように |
| **入出庫の UP はデバイス側、クラウドは記録のみ。予約状態は変えない** | §5.3 安全インターロック。物理安全はデバイスが責任を持つ |
| **予約の変更・キャンセルは reserved のみ可（0件なら 409）** | 利用開始後の状態破壊を防ぐ |
| **bcrypt(パスワード)／refresh は SHA-256(ソルト無)token_hash 照合＋ローテーション、family_id 系統失効、MVP access denylist 無** | refresh は高エントロピー乱数で bcrypt 不要・等値照合が速い。失効は family 単位 |

## 5. 設計上の矛盾・要確認点（重要度順）

### contradictions

| # | 重要度 | 矛盾 | 状態 / 取った対応 |
| --- | --- | --- | --- |
| C1 | **high** | **Fee確定とcompleted遷移の順序が食い違う**。コアフロー④図=「completed→Fee記録」、超過フロー図=「Fee記録→completed」、処理一覧/CLAUDE/DDL=「UPDATE(completed)が1件成功した時だけ Fee INSERT」 | ✅**解消**: 両シーケンス図を「単一トランザクションで条件付きUPDATE(→completed, WHERE status IN active,overstay)が1件成功した時のみ Fee INSERT」に統一。アトミック性で「completed without fee」を、勝者のみ INSERT で「UQ_Fee_resv 二重」を同時に防ぐ |
| C2 | medium | **gate-down の事前NG即時失敗(503)が DOWN失敗フロー図(F4-6)に無い**。OpenAPI は 503(事前NG,retryable=false)/504(無応答,retryable=true)を分けるが、図の alt は 409/504/正常 のみ | ✅**解消**: F4-6 図の alt に 503(device_unhealthy・即時失敗) 分岐を追加、説明とステータス割当メモも 409/503/504 に更新（OpenAPI と一致） |
| C3 | low | **CommandLog.result の値域がDDLとER図で食い違う**。DDL/失敗フロー図は pending を含む(DEFAULT pending)、ER図備考は success/failure のみ | ✅**解消**: ER図備考を `pending`/`success`/`failure`（DDL `CK_Cmd_result` と一致）に修正 |
| C4 | low | **refreshToken 処理が「denylist 参照」と誤記**。実体は RefreshToken テーブル token_hash 等値照合＋ローテーション。MVP は denylist を持たない | ✅**解消**: 処理一覧 refreshToken 行を「token_hash 照合＋ローテーション（条件付き UPDATE で旧失効、family_id 引継ぎ）」に修正 |

### gaps

| # | 重要度 | 欠落 | 実装前に決めるべきこと |
| --- | --- | --- | --- |
| G1 | **high** | **RefreshTokenテーブル＋ログイン試行ロック保持先が正DDL/ER図に未反映**。認証設計§7にDDL案のみ | ✅**解消**: `RefreshToken`（family_id/token_hash(VARBINARY32 UNIQUE)/revoked_at/expires_at）を正DDLとER図に追加。ログインロックは MVP 方針で `[User].failed_attempts` / `lock_until` 列として追加。cleanupTokens の定期削除もメモに記載 |
| G2 | medium | **料金体系・キャンセルポリシー・ノーショー課金が未確定**(§12#1-3)。算定式(超過=max(0,exit−end))はあるが単価が無く Fee 計算不能 | 仮単価を**設定値 or DB のどこに置くか**を決める。見込み額/確定額の計算ソースを一本化 |
| G3 | medium | **ライフサイクル時間値が全て仮**：ノーショー猶予(仮30分)・入庫待ちタイムアウト(仮5分)・バッファB(仮15分)・走査間隔(§12#9)。大小制約(入庫待ち<ノーショー猶予)未確定 | タイマー実装前に3値＋走査間隔を確定。設定値として外出し |
| G4 | medium | **デバイス健全性閾値(last_seen_at許容 仮N分)が未定義**。OpenAPI は availability と gate-down で同一値共有とだけ規定 | 単一設定値として定義（両判定の一致のため）。料金には影響しない |
| G5 | low | **finishUsage 後の即overstay見え問題**。end前倒し→在車のまま次走査で即overstay。許容か猶予かが未決 | G2(料金/キャンセルポリシー)と一緒に決定 |
| G6 | low | **GUID採番主体未確定**（NEWSEQUENTIALIDサーバ採番 か アプリ採番） | backend方針として統一（サーバ採番推奨：断片化緩和） |
| G7 | low | **plate_position が down のまま残るズレ(onPlateUp未達)の検知が無い** | MVP は許容で確定済。将来の定期照合の要否のみ要認識 |

## 6. 未確定事項（§12）の実装への影響

| 未確定項目 | 仮値 | 依存する実装箇所 |
| --- | --- | --- |
| 料金単価・上限・超過単価(#1) | 未定 | `Fee.slot_fee/overstay_fee` 算定、updateReservation の見込み額、getFee |
| キャンセルポリシー(#2) | 未定 | cancelReservation の課金有無、finishUsage 猶予 |
| ノーショー課金(#3) | 未定 | detectNoShow 後の Fee 生成有無（現状は区画解放のみ） |
| バッファ時間 B(#4) | 仮15分 | createReservation の近接予約競合チェック（serializable Tx） |
| 入庫待ちタイムアウト(#5) | 仮5分 | device-sim 自動UP、入庫待ち→予約待機の導出 |
| ノーショー猶予 | 仮30分 | detectNoShow の判定境界 |
| デバイス健全性閾値(#14) | 仮N分 | listSpots/getAvailability/gateDown の健全性判定（**同一値**） |
| タイマー走査間隔(#9) | 未定 | detectNoShow/detectOverstay/autoComplete の周期 vs サーバーレス自動停止 |
| 認証方式(#6) | **自前JWTに確定** | access15分/refresh14日（寿命は仮、調整可） |

> 仮値依存の実装では「仮値である」旨をコメントし、設定値として外出しして確定時に1箇所変更で済むようにする。
