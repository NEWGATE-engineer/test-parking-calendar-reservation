| 項目 | 内容 |
| --- | --- |
| システム名 | 駐車場予約システム（仮） |
| フロントエンド | Flutter / Dart |
| バックエンド | TypeScript（Node.js） |
| インフラ | Azure（App Service / Functions / SQL Database / Storage / Application Insights / Log Analytics / IoT Hub） |
| 版 | v5（デバイス健全性の反映） |

> v5 での主な変更：予約可能性・満空表示にデバイス健全性（最終通信日時）を反映し、不健全な区画を予約不可／状態不明とする（§8・§4.3）。あわせて §5.4 に物理占有競合の注記、通知チャネル（MVP はメールのみ）の方針を追記。

## 1. プロジェクト概要

### 1.1 目的
利用者がアプリから駐車区画を事前予約し、予約に基づいて AUTOSTAND（ロック板）を制御して入出庫できるシステムを構築する。あわせて満空表示・料金計算・利用履歴管理を提供する。

### 1.2 対象ユーザー
一般利用者（会員登録した個人）。管理者機能は将来フェーズで検討する。

### 1.3 スコープ
会員管理・予約・入出庫制御・料金計算・マイページを扱う。物理 AUTOSTAND は学習段階ではソフト擬似デバイスまたは ESP32＋サーボで代替する。

### 1.4 前提・制約
- 認証はメールアドレス＋パスワードを基本とする。
- AUTOSTAND は区画ごとに設置され、満空センサーとロック板（昇降）を備える。
- 平常時（空車・予約なし）、ロック板はアップ（ブロック）を既定とする。
- DOWN はアプリ指示でのみ行い、UP は出庫（空車検知）で自動的に戻る。
- 連続予約の物理占有競合を抑えるため、予約と予約の間にバッファ時間を設ける。
- 通信は IoT Hub を介した双方向通信とする。
- 無料枠で動作させるため、各 Azure サービスは無料ティア／サーバーレスを選択する。

## 2. システム構成

### 2.1 技術スタック

| レイヤー | 採用技術 |
| --- | --- |
| モバイルアプリ | Flutter / Dart |
| バックエンド API | TypeScript（Node.js）/ App Service |

### 2.2 各サービスの役割
- App Service … TypeScript REST API のホスト。
- Functions … 入退場処理、料金計算、メール通知、満空集計、AUTOSTAND への DOWN 指示、予約ライフサイクルの定期処理（超過・ノーショー・自動完了の検知）。
- SQL Database … 会員・予約・利用記録・料金・コマンドログ・デバイスイベントを保持。
- Storage … 区画写真、規約・ポリシー・FAQ などの静的コンテンツ、ログ。
- IoT Hub … 満空テレメトリの受信と、ロック板の DOWN 指示（ダイレクトメソッド）の双方向通信。
- Application Insights … API の監視。

### 2.3 追加で必要となる構成要素（要検討）
- メール送信基盤 … Azure Communication Services（Email）または外部サービス。
- 認証基盤 … 自前実装（JWT＋パスワードハッシュ）か Microsoft Entra External ID か（§12）。

## 3. 用語定義

| 用語 | 定義 |
| --- | --- |
| AUTOSTAND | 区画ごとのロック板装置。満空センサーとロック板の昇降機能を持つ。 |
| 満空 | 区画の物理状態（満＝在車／空＝空車）。センサーが検知する。 |
| アップ | ロック板を上げてブロックする状態。空車・予約なし時の既定で、出庫後は自動的にこの状態へ戻る。 |
| ダウン | アプリ指示でロック板を下げる操作。入庫を可能にし、在車中は下がったまま維持される。出庫（空車検知）で自動的にアップへ戻る。 |
| 予約可能性 | 指定した時間帯にその区画を予約できるか。予約データから算出する（満空とは別概念）。 |
| バッファ時間 | 同一区画で連続する予約の間に必ず空ける時間。物理占有の競合を緩和する。 |
| 入出庫 | 予約期間内に車両が出入りする行為。期間内は複数回可能（再入庫のたびに DOWN 指示が必要）。 |
| 超過 | 予約終了時刻を過ぎても在車している状態。 |
| ノーショー | 予約したが一度も入庫しないまま一定時間が経過した状態。 |
| デバイス健全性 | AUTOSTAND の最終通信が閾値以内であること。健全でない区画は予約不可／状態不明として扱う。 |

#### 4.3.1 予約ライフサイクル（状態）
`予約済 → 利用中 → 完了`（正常系）／途中で `キャンセル`／一度も入庫せず `ノーショー`／終了時刻超過で `超過 → 完了`。

| シナリオ | MVP の扱い |
| --- | --- |
| 利用開始 | 初回の在車検知で「予約済 → 利用中」へ。 |
| 超過滞在 | 在車のまま終了時刻を過ぎたら「利用中 → 超過」。超過分を実時間で追加課金。板は下がったまま維持。 |
| 超過の終了 | 超過中に出庫（空車検知）で「超過 → 完了」とし、超過料金を確定する。 |
| ノーショー | 開始時刻から一定時間（仮：30分）入庫がなければ「ノーショー」とし区画を解放。判定は現在の満空ではなく UsageRecord（入庫記録）の有無で行う。課金は予約金導入まで無し（仮置き、§12）。 |
| 終了申告忘れ | 出庫センサーで空車を検知し、かつ予約終了済みなら自動的に「完了」とする。 |

判定は Functions の定期処理（タイマートリガ）と IoT メッセージで行う。超過の上限・通知・エスカレーションは将来検討（§12）。

#### 4.3.2 重複・近接予約の判定（バッファ込み）
- 同一区画で連続する予約の間に、最低バッファ時間 B（仮：15分）を設ける。
- 競合条件：`new.start < existing.end + B AND existing.start < new.end + B`。これを満たす予約は作成を拒否する。
- Azure SQL には範囲排他制約がないため、登録時はトランザクション分離レベル（serializable）＋競合チェック、またはアプリ側ロックで実装する。
- 予約作成時にも対象区画のデバイス健全性（§8）を確認し、不健全なら作成を拒否する。
- バッファを超える超過が起きた場合、物理的には次の予約者が入庫できない（残存リスク）。MVP では次の予約者の DOWN を失敗とし、F4-6 の失敗導線に乗せる。区画振替・返金は Phase 2（§12）。

### 4.4 入出庫

| ID | 要件 | 区分 |
| --- | --- | --- |
| F4-1 | 有効な予約に基づき、ユーザーのアプリ操作（DOWN 指示）でロック板を下げ、入庫できる | ✅ |
| F4-2 | 在車中はロック板を下げたまま維持する | ✅ |
| F4-3 | 出庫（空車検知）でロック板を自動的に上げる | ✅ |
| F4-4 | 予約期間内は何回でも入出庫できる（再入庫のたびに DOWN 指示が必要） | ✅ |
| F4-5 | 予約なし／予約期間外の DOWN 指示は拒否する（板はアップのまま、入庫不可） | ✅ |
| F4-6 | DOWN 指示が失敗（デバイス応答なし／オフライン／物理占有中）した場合の導線を提供する（リトライ→タイムアウト→失敗通知＋サポート導線） | ✅ |
| F4-7 | DOWN 指示は冪等キー（request_id）を付け、CommandLog で重複指示を吸収する（物理動作の二重発火防止） | ✅ |
| F4-8 | 利用終了の申告ができる（出庫検知でも自動完了。§4.3.1） | ✅ |
| F4-9 | 利用開始・終了時にメール通知を送る | ⏳ |

> DOWN の契機はアプリ操作のみ。UP はデバイス側が空車検知（および §5.3 の安全条件）で自動的に行う。満空センサーは「入庫完了の判定」と「自動 UP の契機」に用い、DOWN のトリガには使わない。

## 5. AUTOSTAND 状態機械

### 5.1 状態

| 状態 | 板位置 | 条件 | 説明 |
| --- | --- | --- | --- |
| ブロック中 | アップ | 予約なし／時間外 | 既定。DOWN 指示は拒否。入庫不可。 |
| 予約待機 | アップ | 有効予約あり・車両外 | ユーザーの DOWN 指示待ち。入庫前・一時外出後を含む。 |
| 入庫待ち | ダウン | DOWN 指示後・車両未入庫 | 板を下げて入庫を待つ一時状態。 |
| 在車中 | ダウン | 予約期間内・在車 | 板を下げたまま駐車。 |
| 超過中 | ダウン | 予約終了後も在車 | 板ダウン維持。追加課金対象。 |

### 5.2 遷移

| From | To | 契機 |
| --- | --- | --- |
| ブロック中 | 予約待機 | 予約開始時刻の到来 |
| 予約待機 | 入庫待ち | ユーザーの DOWN 指示 |
| 入庫待ち | 在車中 | 在車検知（入庫完了） |
| 在車中 | 予約待機 | 出庫（空車検知）→ 自動 UP（予約期間内） |
| 入庫待ち | 予約待機 | タイムアウト（入庫なし）→ 安全条件を満たして自動 UP（§5.3） |
| 予約待機 | ブロック中 | 予約終了／キャンセル／ノーショー確定 |
| 在車中 | 超過中 | 予約終了時刻の到来（在車のまま） |
| 超過中 | ブロック中 | 出庫（空車検知）→ 自動 UP |

> 予約期間内は「予約待機 →(DOWN)→ 入庫待ち →(在車検知)→ 在車中 →(出庫)→ 予約待機」を何度でも繰り返せる。

### 5.3 安全インターロック
- 出庫経路の UP（在車中→予約待機、超過中→ブロック中）は、空車検知（車両が完全に出たこと）を条件に自動実行する。
- タイムアウト UP（入庫待ち→予約待機）は、「在車=false」だけでは不十分。乗り入れ途中はまだ在車判定されないため、次の両方を条件とする：(1) 板エリアに一定時間の連続無検知、(2) UP 動作の直前にデバイスがローカルセンサーを再確認し、検知があれば中止。
- 在車中・超過中は板ダウンを維持する。
- 接近センサーがあれば (1) の判定に併用する（将来オプション）。MVP は「連続無検知＋動作直前の再確認」で代替する。

### 5.4 予約状態 × デバイス状態の対応表

| 予約状態 | 対応するデバイス状態 | 主な遷移契機（Functions トリガ） |
| --- | --- | --- |
| 予約済（開始前） | ブロック中 | — |
| 予約済（開始後・未入庫） | 予約待機 →(DOWN)→ 入庫待ち | 予約開始（タイマー）／ DOWN 指示（HTTP→IoT ダイレクトメソッド） |
| 利用中 | 在車中（一時外出時は 予約待機・入庫待ち） | 初回の在車検知（IoT メッセージ）で 予約済→利用中 |
| 超過 | 超過中 | 終了時刻到来かつ在車（タイマー）で 利用中→超過 |
| 完了 | ブロック中 | 出庫（空車検知, IoT）かつ終了済み、または利用終了申告（HTTP）。超過中なら超過料金を確定。 |
| キャンセル | ブロック中 | ユーザー操作（HTTP） |
| ノーショー | ブロック中 | 開始からタイムアウトかつ未入庫（タイマー、UsageRecord 無で判定） |

> 物理占有競合の例外：超過がバッファを超えると、res A が「超過中」のまま res B の開始時刻が来て、一瞬 2 つの予約が同一デバイスに乗る。これは §4.3.2 の残存リスクとして受容済みで、res B は予約待機にならず F4-6 へ回す。

この対応表が、Functions の各遷移処理（どのトリガで予約状態とデバイス指示を更新するか）の実装指針となる。

## 6. 非機能要件

### 6.1 セキュリティ
- パスワードは必ずハッシュ化（bcrypt 等）。平文保存はしない。
- 全通信は HTTPS / TLS。
- SQL アクセスはパラメータ化クエリ／ORM で SQL インジェクションを防止。
- JWT は短い有効期限＋リフレッシュトークンで運用。失効が必要な場合は denylist。
- ログインにレート制限・アカウントロックを設けブルートフォースを抑止。
- IoT Hub はデバイスごとに個別認証。
- ゲート操作（物理アクセス制御）は CommandLog と DeviceEvent に記録する。

### 6.2 パフォーマンス
- 満空表示は、デバイスの状態変化からおおむね数秒以内にアプリへ反映。
- 主要 API のレスポンスは、サーバーレスの自動停止からのコールドスタート時を除き 1 秒以内を目標（学習用の目安）。
- サーバーレスの自動一時停止までの遅延設定は検討事項とする（§12）。

### 6.3 可用性
- 学習用のため高可用性は必須としないが、マネージドサービスの自動バックアップ等を前提とした設計とする。

### 6.4 監視・ログ
- Application Insights で API のリクエスト数・レスポンス時間・失敗率・例外を監視。
- Log Analytics に各サービスのログを集約し KQL で分析。
- AUTOSTAND の死活（最終通信時刻）と状態遷移（DeviceEvent）を監視。
- 無料枠超過を避けるためログのサンプリングと保持期間を設定。

### 6.5 保守性
- フロント／バックエンドの責務を分離し API 仕様を明確化。
- 環境（開発・本番）ごとに設定を分離。

## 7. データモデル概要

| エンティティ | 主な項目 | 説明 |
| --- | --- | --- |
| 会員（User） | id, email, password_hash, 氏名, 状態(有効/退会), 作成日時 | ポイントは Phase 2 のため MVP 物理スキーマでは保持しない。 |
| 同意記録（Consent） | id, user_id, 規約バージョン, 同意日時 | 規約・ポリシー同意の記録。 |
| 駐車区画（ParkingSpot） | id, 区画名, 現在の在車状態(在車/空車), device_id | 物理状態のみを持つ。予約状態は持たせない。 |
| AUTOSTAND（Device） | device_id, spot_id, 現在のロック板位置(アップ/ダウン), 最終満空状態, 最終通信日時 | デバイス情報。 |
| 予約（Reservation） | id, user_id, spot_id, 開始日時, 終了日時, 状態(予約済/利用中/完了/キャンセル/ノーショー/超過), 作成日時 | 予約可能性はこのテーブルから算出。 |
| 利用記録（UsageRecord） | id, reservation_id, 入庫日時, 出庫日時 | 予約期間内の複数回入出庫を記録。ノーショー判定にも用いる。 |
| 料金（Fee） | id, reservation_id, 予約枠料金, 超過料金, 合計, 計算日時, 状態 | 料金計算結果。 |
| コマンドログ（CommandLog） | id, reservation_id, user_id, request_id(冪等キー), 種別(DOWN), 指示日時, 結果(成功/失敗), デバイス応答日時 | DOWN 指示の監査・冪等管理。 |
| デバイスイベント（DeviceEvent） | id, device_id, reservation_id, 種別(DOWN実行/UP/在車検知/空車検知), 発生日時 | 状態遷移の記録。監査・デバッグ用。 |
| 通知ログ（Notification） | id, user_id, 種別, 送信日時, 状態 | 送信メールの記録。 |

> 日時はすべて UTC で保存し、表示時に JST へ変換する。

## 8. 満空表示と予約可能性の使い分け

| 用途 | 参照する情報 | 由来 |
| --- | --- | --- |
| 当日・即時利用の表示 | 現在の在車状態（在車／空車）。最終通信が古ければ「状態不明」 | センサー（テレメトリ）＋ Device.最終通信日時 |
| 入庫完了の判定 | 在車検知 | センサー |
| 出庫による自動 UP の契機 | 空車検知（＋§5.3 安全条件） | センサー |
| 事前予約の可否表示（best-effort） | 対象時間帯の予約有無＋バッファ、かつデバイス健全 | Reservation テーブル ＋ Device.最終通信日時 |

- 通常は「在車 ↔ 板ダウン」「空車 ↔ 板アップ（既定）」が対応する。例外は「入庫待ち（DOWN 指示後〜入庫前）」で、板ダウン・空車の一時状態。
- デバイス健全性：`Device.最終通信日時` が閾値（仮：N 分）以内であることを健全とみなす。健全でない区画は、予約可能性では「予約不可」として除外し、満空表示では「状態不明」とする。これにより、壊れた／オフラインの区画をユーザーが予約して当日 DOWN できず F4-6 に落ちる事態を未然に防ぐ。
- ただし、予約後〜利用日の間にデバイスが不健全化する可能性は残る（残存リスク）。その場合は F4-6 の失敗導線が最終的な受け皿となる。予約済み区画の不健全化に対する事前通知・振替は将来検討（§12）。
- 予約可能性の表示（availability）は参照時点の暫定値（best-effort）であり、確定判定は予約作成時の競合チェック＋デバイス健全性確認（§4.3.2）で行う（TOCTOU を許容）。

## 11. IoT連携（AUTOSTAND）詳細

### 11.1 デバイス → クラウド（テレメトリ）
- 満空センサーの状態（在車／空車）を IoT Hub に送信。
- Functions で受信し、区画の現在の在車状態を更新。入庫完了の判定や出庫検知（自動完了・超過終了の判定）に用いる。
- DOWN 実行・UP・在車・空車の遷移は DeviceEvent として記録する（DOWN 指示だけでなく UP・満空遷移も残す）。

### 11.2 クラウド → デバイス（コマンド）
- クラウドからの指示は DOWN のみ。有効な予約に基づき、アプリ操作を契機に IoT Hub のダイレクトメソッドで送る。
- DOWN 指示は冪等キー（request_id）を伴い、CommandLog で重複を吸収。デバイス側も同一 request_id の二重発火を防ぐ。
- UP はデバイス側が空車検知（＋§5.3 の安全条件）で自動実行する。
- 予約なし／予約期間外／物理占有中の DOWN は拒否または失敗とし、F4-6 の導線に乗せる。
- 応答失敗（オフライン）時は、リトライ → タイムアウト → 失敗通知＋サポート導線を提供する。

### 11.3 通信前提と将来の代替手段
- DOWN 指示はアプリの通信を前提とする。地下・立体駐車場での電波断は既知の失敗モード。
- 将来の代替手段（現地ボタン／QR／BLE）の余地を残す。

### 11.4 学習段階の代替
- 物理デバイスの代わりに Azure IoT デバイス SDK（`azure-iot-device`）で擬似 AUTOSTAND を実装。状態機械（§5）に従わせる。
- DOWN 指示受信で「下げる」、在車・空車の擬似トリガで遷移・自動 UP を再現。
- タイムアウト UP は、§5.3 の安全条件（連続無検知＋動作直前の再確認）を擬似デバイスのロジックに必ず実装する。
- 物理動作を確認したい場合は ESP32＋サーボ＋センサーで代替。
