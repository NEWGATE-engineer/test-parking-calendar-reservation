# ハーネス設計プレイブック（別プロジェクト移植用）

> このファイルを新規プロジェクトの Claude（Claude Code）に渡し、
> 「このプレイブックに沿って、このリポジトリ用のハーネスを段階的に作って」と指示すれば、
> 同等の "エージェント用足場" を構築できる。**スタック非依存**（例は TypeScript だが置換可）。

---

## 0. ハーネスとは

LLM（エージェント）が "たまたま良い" ではなく **"毎回確実に良い" 出力を出すよう、モデルの周りの環境＝足場を工学的に作り込むこと**。モデル本体は触らず、その **入力（文脈）・道具・フィードバック・制約** を設計する。

人間に例えると「優秀な新人に、オンボーディング資料・権限・CI・コードレビュー・承認フローを整えて、安定して良い PR を出させる」のと同じ営み。

### 構成要素モデル（①〜⑩）

| # | 要素 | 中身 | 本プレイブックでの実体 |
| --- | --- | --- | --- |
| ① | 文脈 Context | 規約・ドメイン知識・「良い実装とは」を常に渡す | `CLAUDE.md` |
| ② | 道具 Tools / 権限 | 使えるツールと許可スコープ | `.claude/settings.local.json` ＋ MCP |
| ③ | 役割分担 Subagents | レビュー/調査など特化エージェント | `.claude/agents/*.md` |
| ④ | オーケストレーション | 複数ステップ/並列/判定の協調 | ダイナミックWF ＋ `.claude/workflows/*.js` |
| ⑤ | フィードバック・検証 | テスト・型・lint・CI・自動レビュー | テスト ＋ CI ＋ **commit 前 Hook** |
| ⑥ | ゲート / ガードレール | 重大度ゲート・承認・ブランチ保護 | レビュー起動コマンド ＋ ブランチ運用 |
| ⑦ | 収束・コスト制御 | 増分再レビュー・いつ止めるか | レビューの自動 baseline |
| ⑧ | 観測 Observability | ログ・トランスクリプト | 既定のトランスクリプト |
| ⑨ | 記憶 Memory | セッションを跨ぐ恒久知識 | Claude のメモリ機能 |
| ⑩ | 評価 Eval harness | エージェント品質をデータセットで計測 | **後回し推奨**（下記） |

### 設計の原則
- **価値の高い順に積む**：①文脈 → ⑤検証 → ④/⑥ レビュー自動化が最優先。装飾は後。
- **MVP は最小から**：必要になってから足す（Just-In-Time）。ただし⑤の Hook は安く効くので早めに。
- **過剰投資を避ける**：ハーネスを磨くこと自体が目的化しやすい。ハーネスは "良いプロダクトを速く正しく作る手段"。手が止まったらプロダクトに戻る。
- **⑩ eval は時期尚早になりやすい**：計測対象（エージェント出力の蓄積）と正解ラベルが要る。レビューが何度か回って実績が貯まってから小さく着手する。

## 1. 構築ロードマップ（推奨順）

```
Step0 文脈(CLAUDE.md)          ← まずこれ。全エージェントの土台
Step1 権限(settings.local)      ← 安全に動かす
Step2 レビューエージェント+コマンド ← 品質の最大レバレッジ
Step3 CI連携(@claude)           ← PR で自動レビュー
Step4 メモリ運用                ← 知見の蓄積
Step5 Hook(commit前 検証)       ← 検証ループの自動化（安く効く）
Step6 Skills(反復作業の手順化)
Step7 名前付きワークフロー       ← 育った定番を保存
（後で）⑩ eval harness
```

## 2. 各コンポーネントの作り方（テンプレ付き）

### 2.0 ディレクトリ構成（完成形）
```
<repo>/
├─ CLAUDE.md                         # ① 文脈
├─ .claude/
│  ├─ settings.json                  # ⑤ Hook（チーム共有・コミット対象）
│  ├─ settings.local.json            # ② 個人の権限（gitignore 推奨）
│  ├─ agents/*.md                    # ③ レビュー観点エージェント
│  ├─ commands/review-pr.md          # ⑥ レビュー起動コマンド
│  ├─ hooks/pre-commit-quality.sh    # ⑤ Hook 実体
│  ├─ skills/<name>/SKILL.md         # 反復作業の手順
│  └─ workflows/<name>.js            # ④ 名前付きワークフロー
└─ .github/workflows/claude.yml      # ③ CI でエージェント起動
```

### 2.1 ① CLAUDE.md（最重要）
全エージェントが最初に読む共有知識。次を簡潔に書く：
- **プロジェクト概要**（何を作るか・現状フェーズ）
- **技術スタック表**（層・技術・配置）
- **開発コマンド**（ビルド/テスト/起動）
- **ドメインの重要ルール**（"必ず守る不変条件"。例：状態遷移は条件付きUPDATE、時刻はUTC保存、パラメータ化クエリ、冪等性）
- **コーディング規約**（コメント/命名/エラー方針）
- **やってはいけないこと**（秘密のコミット禁止、平文パスワード禁止 等）
- **未確定事項**（仮値で進める箇所を明示）

> ポイント：抽象論でなく「このリポジトリ特有の落とし穴と決め事」を書く。長文より "守るべき不変条件" の箇条書きが効く。

### 2.2 ② 権限 `.claude/settings.local.json`
よく使う安全な操作を許可リスト化（毎回確認を減らす）。秘密に触れる操作は入れない。
```json
{
  "permissions": {
    "allow": [
      "Bash(git add *)", "Bash(git commit *)", "Bash(git push *)",
      "Bash(npm run *)"
    ]
  }
}
```

### 2.3 ③ レビュー観点エージェント `.claude/agents/<観点>-reviewer.md`
観点を分けた専門レビュアを複数用意（並列で多角的に叩く＝reflection パターン）。推奨5観点：
**code-quality / security / performance / test-coverage / documentation-accuracy**。

雛形（frontmatter ＋ 本文）：
```markdown
---
name: security-code-reviewer
description: OWASP・入力検証・認証認可・機密漏洩の観点で PR をレビューする
---
あなたは <スタック> のセキュリティレビュア。差分のみをレビューし、
重大度（critical/high/medium/low）と該当 file:line、修正案を必ず付ける。
このリポジトリの CLAUDE.md のドメイン規約違反を最優先で指摘する。
推測の指摘は避け、コードで裏取りできたものだけ報告する。
```
> 各 reviewer の本文は「対象スタック・見る観点・出力フォーマット（重大度＋file:line＋修正案）・誤検知を避ける指示」を含める。

### 2.4 ⑥ レビュー起動コマンド `.claude/commands/review-pr.md`
5エージェントを**並列起動**し、結果を統合して**重大度ゲート**（critical/high が無ければ GO 等）で判定するオーケストレーション手順。要点：
- 各 reviewer を並列に呼び、findings を集約・重複排除。
- **重大度ゲート**：critical/high があれば NO-GO、サマリに一覧。
- **増分（自動 baseline）**：前回サマリに `<!-- reviewed-at: <SHA> -->` を埋め、引数なし再実行時はそこからの差分だけ見る → 収束（同じ指摘を蒸し返さない）。

### 2.5 ③+CI `.github/workflows/claude.yml`（PR で自動レビュー）
`claude-code-action` を使い、PR コメントでエージェントを起動。**実体験の落とし穴2点（重要）**：
- **トリガには `@claude` プレフィクスが要る**プロジェクトがある（素の `/review-pr` は無視されることがある）。`@claude /review-pr` の形にする。
- **`.claude/commands` や `agents` は "デフォルトブランチ" に存在しないと CI から見えない**。feature ブランチだけに置くと CI が 0 秒で汎用応答して失敗する。**ハーネス定義は先に main/develop に入れる**こと。

### 2.6 ⑨ メモリ運用
セッションを跨ぐ恒久知識を1ファイル1事実で保存し、索引（MEMORY.md）に1行追記。保存すべきは「コードから読み取れない決定・好み・運用」。コード構造や git 履歴は保存しない。

### 2.7 ⑤ Hook（commit 前に検証を強制）★安く効く
コミット直前に型チェック＋テストを自動実行し、赤ならコミットを止める。"手で叩く" 運用を構造的に強制＝検証ループの自動化。

`.claude/settings.json`（チーム共有・コミット対象）:
```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [ { "type": "command",
          "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/pre-commit-quality.sh" } ] }
    ]
  }
}
```

`.claude/hooks/pre-commit-quality.sh`（要 `chmod +x`）:
```bash
#!/usr/bin/env bash
set -euo pipefail
# Claude Code はツール入力を JSON で stdin に渡す。コマンド文字列を取り出す。
# （jq が無い環境が多いので node で抽出するのが移植性◎）
payload="$(cat)"
command_str="$(printf '%s' "$payload" | node -e 'let d="";process.stdin.on("data",c=>d+=c).on("end",()=>{try{const j=JSON.parse(d);process.stdout.write((j.tool_input&&j.tool_input.command)||"")}catch{process.stdout.write("")}})')"
# git commit のときだけ発火
case "$command_str" in *"git commit"*) ;; *) exit 0 ;; esac
# 対象ディレクトリに変更が無ければスキップ（重いテストを無駄に回さない）
root="$(git rev-parse --show-toplevel 2>/dev/null || echo .)"
if ! git -C "$root" diff --cached --name-only | grep -q '^<対象ディレクトリ>/'; then exit 0; fi
cd "$root/<対象ディレクトリ>"
# 失敗したら exit 2 でコミットをブロック（stderr がモデルに戻る）
if ! <型チェックコマンド>; then echo "中止: 型チェック失敗" >&2; exit 2; fi
if ! <テストコマンド>;   then echo "中止: テスト失敗"   >&2; exit 2; fi
exit 0
```
> 設計：①重い検証を「commit 時・対象変更時のみ」に絞る ②`exit 2` でブロック ③壊れた入力でも安全に通過（fail-open でコミット自体は壊さない）。

### 2.8 Skills `.claude/skills/<name>/SKILL.md`（反復作業の手順化）
`php artisan make:*` のジェネレータ＋手順書のような部品。**繰り返す定型作業**を、規約どおりに迷わず実行させる。
```markdown
---
name: new-endpoint
description: 新エンドポイント追加時に使う。<レイヤ構成>に沿って雛形・テスト・ドキュメント同期まで漏れなく進める。
---
# 手順チェックリスト
1. 設計（API仕様）を確認
2. <レイヤ1> → <レイヤ2> → ... を "手本ファイル" に倣って実装
3. テスト（単体＋HTTP）
4. ドキュメント同期
## 完了の定義
- [ ] ...
```
> コツ：**"手本となる既存モジュール" を正本として指定**する（「`src/<手本>/` に倣え」）。抽象説明より実例参照が効く。作るのは "繰り返す作業" だけ（1回限りには不要）。

### 2.9 ④ ワークフロー（並列オーケストレーション）
**ダイナミック（その場書き）** と **名前付き（`.claude/workflows/*.js` に保存）** がある。判断は §3。
名前付きの雛形（判定パネル＝設計判断を多角的に決める汎用WF）の骨子：
```js
export const meta = { name: 'design-judge-panel', description: '...', phases: [...] }
const input = typeof args === 'string' ? { question: args } : (args || {})
// ① 異なる観点で N 案を並列生成（barrier：統合に全案要る）
const candidates = (await parallel(ANGLES.map(a => () => agent(prompt(a), {schema: CAND})))).filter(Boolean)
// ② 各案を複数レンズで採点（案×レンズ並列）
const judged = await parallel(candidates.map(c => () =>
  parallel(LENSES.map(l => () => agent(judgePrompt(c,l), {schema: VERDICT})))))
// ③ 全案＋採点を1人が統合して推奨
return await agent(synthesizePrompt(judged))
```
> 構造化出力は `schema`（JSON Schema）でモデルに強制すると後段が安定する。`agent()` 失敗は `null` を返すので `.filter(Boolean)`。

## 3. ワークフロー判断ガイド

**そもそもワークフロー（並列）を使うのは：**
- 並列の幅がある（多ファイル/独立ユニットへ fan-out）／敵対的に検証したい（判定パネル・多数決）／1コンテキストに収まらない規模。
- 逐次・相互依存・単一ユニットの実装には**使わない**（空回り）。

| | ダイナミック | 名前付き |
| --- | --- | --- |
| いつ | 一回限り・形が未確定・探索的 | 同じ型を入力を変えて繰り返す |
| 例 | 「この docs を読み解く」 | 「設計判定パネル（毎回別テーマ）」 |
| 昇格 | まず試作 → 役立って繰り返すと分かったら → | 名前付きに保存して再利用 |

**型の使い分け（目的別）：**
- 案が割れる判断を決める → **判定パネル**
- 既存設計/コードを理解する → **並列リーダー fan-out**
- 多観点でレビュー → **レビュー fan-out（5観点）**

## 4. やってはいけない / 落とし穴（実体験）

- ❌ ハーネス磨きの目的化。手が止まったらプロダクトに戻る。
- ❌ ⑩ eval を最初に作る（計測対象が無く徒労）。実績が貯まってから。
- ❌ Hook に重すぎる検証を全 commit で回す → "対象変更時のみ＋commit時のみ" に絞る。
- ❌ レビュー定義を feature ブランチだけに置く → CI から見えない。**先にデフォルトブランチへ**。
- ❌ トリガ語を間違える → そのアクションが要求する形（例 `@claude ...`）に合わせる。
- ❌ 秘密を argv やリポジトリに置く → 環境変数（名前渡し）/ Key Vault。
- ❌ 状態遷移を「読んで無条件 UPDATE」→ 必ず現在状態を WHERE に（0件=競合）。

## 5. スタック別の置き換え早見

| プレースホルダ | TypeScript 例 | 置き換える対象 |
| --- | --- | --- |
| `<型チェックコマンド>` | `npm run typecheck`（`tsc --noEmit`） | 静的型/Lint（Python: `mypy`/`ruff`、Go: `go vet`、PHP: `phpstan`） |
| `<テストコマンド>` | `npm test`（vitest） | テストランナー（pytest / go test / phpunit 等） |
| `<対象ディレクトリ>` | `backend` | コードのルート |
| `<レイヤ構成>` | validation→router→service→repository | プロジェクトの層 |
| `<手本ファイル>` | `src/spots/` | 既存の良い実装 |
